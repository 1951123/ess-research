# Issue #47 Stage 2A result report

Evidence status: **SUPPORTED_FOR_FROZEN_GATE**, with the qualification that
the candidate-considered ledger is source-derived under the explicit premises
below. This is a bounded **experimentally observed** PostgreSQL 16.14 result,
not a universal PostgreSQL theorem, a claim about all queries, or a shared
cross-task policy result.

## Scope and frozen inputs

The first protocol/input-only commit was `a43b1c8`. Before the outcome run, a
small manifest correction committed as `7cf3874` made the missing-endpoint
control use the intended resource. The v1 full run was retained after its
high-cardinality `(e,f)` object unexpectedly had 1000 MCV items. A source-level
control probe then showed that dropping/recreating that object with extended
statistics target 0 yielded `stxdmcv IS NULL`; amendments `4d8f819` and
`8ee08be` recorded that mechanism and moved the missing-endpoint control to a
separate positive-MCV `(a,f)` object. The corrected v3 run is the evidence
reported here; v1 and v2 were not overwritten.

The v3 fixture has 20,000 deterministic rows generated by `fixture.sql`, six
user attributes `a`--`f`, eight labeled candidate definitions, ten equality
queries, eleven setup/order combinations, and two repetitions per setup/order.
The positive candidate objects had non-empty MCV payloads. `e45` was the
target-0 no-MCV control; `e05` was the positive-MCV missing-endpoint control.

## Observed selection patterns

For each topology, the two catalog orders produced the following selected
labeled resources, repeated twice per order:

- 3-path `{e01,e12,e23}`: `{e01,e23}` and `{e23,e01}`.
- 3-edge star `{e01,e12,e13}`: `{e01}` and `{e13}`.
- Disconnected pair `{e01,e34}`: `{e01,e34}` and `{e34,e01}`.
- Parallel labeled pair `{e01,p01}`: `{e01}` and `{p01}`.

Every listed set passed pairwise-disjointness and inclusion-wise maximality in
the source-ledger graph. These observations support the frozen fixture only;
they do not show that arbitrary OID orders can be realized in one catalog or
that all PostgreSQL workloads have this structure.

## Control interpretation

- **No-MCV control:** `e45` had `mcv_payload_present=false`, `mcv_item_count=-1`,
  and `source_loaded=false`. The pinned source's
  `get_relation_statistics_worker` adds an MCV `StatisticExtInfo` only when
  `statext_is_kind_built` succeeds. The source ledger therefore predicts no
  MCV selector entry; the trace correctly has no selected OID. This is an
  `OUTSIDE_GATE` control, not a usable edge.
- **Missing-endpoint control:** positive-MCV `e05=(a,f)` had 1000 MCV items,
  but `q_missing_endpoint_control` predicates only on `a`. The source ledger
  records one matched endpoint, no selection, and a terminating
  `candidate=none`; the reduced usable graph is empty and the control passes
  fail-closed exclusion.
- **Empty resource control:** with no extended-statistics objects,
  `statext_mcv_clauselist_selectivity` returns before emitting the instrumented
  candidate-none event. Those four observations are `INCONCLUSIVE`, not
  silently treated as a traced empty matching.

## Why the considered-candidate gate is source-derived

The ledger is complete only under these explicitly checked premises:

1. the fresh table has only the declared extended-statistics objects;
2. the catalog rows and `stxkeys` map exactly to the declared labeled
   two-column candidates, with the catalog OID order used by the selector;
3. the query crosswalk has exactly one simple equality clause per distinct
   relevant attribute, with no joins, expressions, OR, ranges, repeated
   attributes or unsupported overloads;
4. the run uses the table owner, no RLS/security-barrier complication, and no
   other estimator has pre-consumed these clauses; and
5. the selected OIDs and every claimed clause index reconcile with the
   source-indexed ledger.

Under those premises, the ledger mirrors the pinned
`choose_best_statistics` coverage/tie rules and the repeated
`statext_mcv_clauselist_selectivity` loop. The existing instrumentation does
not independently print a positive considered/rejected line for every
unselected object; the ledger is therefore not a new runtime trace field and
does not justify a broader claim than its premises.
