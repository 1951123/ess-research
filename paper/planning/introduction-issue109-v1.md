## 1. Introduction

Cardinality estimation is a central input to cost-based query optimization. Errors in estimated cardinalities can propagate through plan costing and contribute to poor execution-plan choices. Database systems therefore maintain statistics that summarize data distributions, and extended statistics can capture relationships among attributes that single-column summaries may miss. However, statistics are not free: their collection and refresh consume resources, and a database administrator or automated advisor must decide which candidate statistics to maintain under a limited budget. This motivates **extended-statistics selection (ESS)**: choosing a resource set that improves estimates for a target workload while respecting maintenance constraints. **[Literature citation needed: cardinality estimation, extended statistics and statistics-selection/physical-design work.]**

A resource set is not necessarily a complete specification of how an estimator uses it. In particular, two extended-statistics objects may cover overlapping predicates. Even when both objects have been created and their contents are fixed, the estimator may be unable—or may be designed not—to apply both objects in the same estimation step. Its choice may depend on an internal priority, a tie-breaking rule, or other scheme-selection behavior that is not exposed to the advisor. Thus, the same *unordered* installed set can admit more than one feasible way of using statistics. When the application policy is unknown or insufficiently characterized, evaluating a resource set under one assumed scheme can conceal estimation outcomes under other admissible schemes. This is the starting point of our study: **uncertainty about the estimator's application strategy is itself a consideration in the resource-selection problem.**

Consider four attributes \(A,B,C,D\) in a query with compatible single-attribute conjunctive predicates. Suppose three candidate pairwise statistics objects summarize the pairs \(AB\), \(BC\), and \(CD\), respectively. Their overlap structure forms a three-edge path: the object on \(BC\) conflicts with each neighboring object, whereas the objects on \(AB\) and \(CD\) do not conflict with one another. If an application scheme must select a set of non-overlapping objects that cannot be extended with any remaining eligible object, the installed set \(\{s_{AB},s_{BC},s_{CD}\}\) admits two inclusion-maximal choices: \(\{s_{AB},s_{CD}\}\) and \(\{s_{BC}\}\). A priority-greedy selector chooses the second if it considers \(s_{BC}\) first, but chooses the first if it considers \(s_{AB}\) or \(s_{CD}\) first. Both choices respect the same installed set and the same statistics contents. They can nevertheless produce different cardinality estimates because they apply different information. **The advisor chooses what is available; the estimator's strategy determines what is actually applied.** Figure 1 should illustrate this path and its two maximal matchings. This example is a deliberately restricted, model-level description of pairwise statistics application, not a claim that every PostgreSQL query follows matching semantics.

The choice matters to the *resource-selection decision*, not only to the estimator's internal execution. To see why, consider a purely illustrative task loss assigning 0.1 to the scheme \(\{s_{AB},s_{CD}\}\) and 2.0 to \(\{s_{BC}\}\). If only \(s_{AB}\) and \(s_{CD}\) are installed, the former is the sole inclusion-maximal matching and both nominal and task-wise worst loss equal 0.1. If \(s_{BC}\) is additionally installed, a priority policy favoring the two nonoverlapping objects still obtains loss 0.1, whereas a policy favoring \(s_{BC}\) obtains loss 2.0; the task-wise pessimistic loss is therefore 2.0. **Making another statistic available can enlarge or change the set of admissible *complete* schemes without improving—and sometimes while worsening—the worst modeled loss.** This numerical illustration is hypothetical, not a measured PostgreSQL outcome or a claim about the calibration of these particular statistics. It motivates explicitly accounting for scheme choice before selecting statistics under a budget.

This uncertainty must be distinguished from two familiar but different sources of variation. **Statistical or sample uncertainty** concerns changes in the underlying data or in the samples used to build statistics; one can control it experimentally by holding the database and sampled statistics contents fixed. **Workload generalization** concerns whether statistics selected using one collection of queries remain useful for unseen queries; it is evaluated by separating training and held-out workloads. **Estimator-strategy uncertainty**, by contrast, concerns which *complete estimation scheme* is applied when a fixed set of candidate resources is available. It can matter even with a fixed database, a fixed sample, and a fixed query. Moreover, the problem does not require that the DBMS randomize its decisions: a deterministic but unknown, inaccessible, or deployment-dependent application rule can create the relevant information gap for an advisor.

We study this gap by separating the *resource decision* from the *admissible application schemes*. The advisor chooses an unordered set \(M\) subject to a maintenance budget. For each cardinality-estimation task \(q\), a prescribed family \(\Gamma_q(M)\) describes the complete schemes regarded as feasible with that set. The estimator and a loss function assign an estimation loss to each scheme. This interface accommodates different degrees of information about the application policy and does not assume that the prescribed family exactly reproduces every behavior of a deployed DBMS. In a structured instantiation motivated by pairwise multivariate most-common-value (MCV) statistics, candidates are labeled edges between attributes, overlap induces conflicts, and the admissible schemes are **inclusion-maximal matchings** among the task-applicable selected edges. The distinction between a *maximal* matching and a *maximum-cardinality* matching is important: the former cannot be augmented, whereas the latter is largest.

The example suggests a modeling choice: should the advisor evaluate the scheme induced by one defensible priority, or guard against every scheme allowed by its admissibility model? Different knowledge of the strategy motivates different selection objectives. **Nominal** evaluates each candidate set under a fixed priority policy, appropriate when that policy is specified and sufficiently predictive. **PESS** evaluates each task under its largest loss among the prescribed admissible schemes and minimizes the aggregate task-wise pessimistic loss, appropriate as a deliberately conservative model when a dependable shared selection policy cannot be assumed. These are not merely two algorithms competing to approximate the same objective; they encode different assumptions about information available to the advisor. To clarify their relationship, we also analyze two counterfactual objectives induced by *one common global priority order across tasks*: the expected loss under uniformly distributed orders and the largest aggregate loss over all such orders. For a fixed set \(M\), if every priority-induced scheme is admissible and all losses are compatible, the expected global-order loss is at most the worst shared-global-order loss, which is at most the task-wise PESS loss. The second inequality can be strict because the worst scheme for one task may be incompatible with the worst scheme for another under a single global order. These model inequalities neither compare resource sets returned by greedy search nor predict physical held-out error.

PostgreSQL offers a concrete, bounded setting in which to examine the relevance of this abstraction. In PostgreSQL 16.14, source inspection of the extended-statistics MCV path identifies candidate-ranking and tie behavior involving the ordered list of statistics objects. Under restricted conditions—simple single-table conjunctions, one compatible clause per distinct attribute, built two-column MCV objects, and no interference from other estimators—the selector's choices correspond to an inclusion-maximal matching. The catalog's statistics-object OID order can affect how ties are resolved. A fixed installation is not thereby stochastic; rather, controlled changes to object creation order can change the priority relation while retaining the same unordered set of selected statistics. Source-derived propositions and scoped tracing support this mechanism, and controlled physical experiments test its effect on actual estimates. We do **not** equate the abstract family of all matchings with unrestricted PostgreSQL behavior or assert that production systems sample OID orders uniformly.

We investigate three questions. **RQ1** asks whether changes in the ordering of overlapping statistics alter the objects applied and cardinality estimates in real PostgreSQL. **RQ2** asks how fixed-priority and task-wise pessimistic selection affect the selected resource sets and their sensitivity to priority in the frozen *training model*. **RQ3** asks how those frozen sets compare in physical held-out estimation error under a *hypothetical uniform distribution over global relative-OID orders*. The last distribution is a counterfactual evaluation choice, not the originally motivating uncertainty model or an assertion about actual OID assignment probabilities.

Our evaluation uses four original AreCEL workloads—Forest10, Census13, DMV11, and Power7—and separates model construction and selection from physical testing. Nominal and PESS select resources exclusively from the original training workloads using the same budget-constrained, strictly improving, add-only greedy procedure. We then evaluate the frozen choices on the original official Test workloads through PostgreSQL 16.14's top-level `Plan Rows`, with the benchmark's zero-aware Q-error definition. The physical comparisons keep the data, PostgreSQL settings, and replayed ANALYZE samples controlled. Complementary analysis exactly enumerates priority permutations for the frozen training-model sets, while a separate physical experiment evaluates sampled global relative-OID permutations on the held-out workloads. Neither enumeration of modeled losses nor sampled physical order evaluation is substituted for the other; no test outcome is used to reselect statistics.

The results show both why strategy uncertainty is consequential and why its treatment involves a trade-off. In a controlled canonical-versus-reverse-order intervention on the four Nominal-selected five-object configurations, Test P95 Q-error increases from \(6.25\) to \(8.00\) on Census13 and from approximately \(22.23\) to \(36.00\) on DMV11, while the corresponding change on Power7 is slightly favorable to the reversed order. Thus, ordering can matter materially, but reversal is not a generally worst-case policy. Under the later counterfactual uniform global-order evaluation, the estimated difference in *expected per-order Test P95* between PESS- and Nominal-selected configurations is negative on Census13 and DMV11, positive on Forest10, and inconclusive within the approximate permutation-sampling interval on Power7. This physical evaluation consists of a frozen 156-configuration sampled design with complete six-order censuses for two three-object sets, **not** a full enumeration of all five-object orders. Its approximate intervals quantify permutation-sampling uncertainty only, not variation over new Test workloads. These results do not establish PESS as universally more accurate; they show that optimizing under one assumed strategy and evaluating over a different family of strategies can favor different resources.

In summary, this paper makes four contributions:

1. **Problem formulation.** We make estimator application/selection uncertainty explicit in budgeted extended-statistics selection, separating the unordered resource decision, complete admissible schemes, modeled losses, and maintenance constraints without presuming a universal database policy.
2. **Objective relationships.** We distinguish fixed-policy Nominal selection, task-wise pessimistic PESS selection, and shared-global-priority risk objectives, providing conditional fixed-set bounds and explaining why task-wise worst cases need not be jointly attainable.
3. **Scoped systems connection.** We connect a pairwise-MCV maximal-matching abstraction to a restricted PostgreSQL 16.14 selection path using versioned source reasoning and controlled physical evidence of OID-priority effects.
4. **Empirical characterization.** We analyze frozen Train-selected resources with exact offline priority enumeration and evaluate them on official held-out PostgreSQL estimates, including a prespecified sampled counterfactual order distribution. The comparison characterizes dataset-dependent estimation accuracy and sensitivity to application-order uncertainty, together with the limits of conservative resource selection.

The remainder of the paper formalizes the resource-and-scheme interface and its pairwise matching instantiation; presents the alternative selection objectives and shared greedy procedure; examines PostgreSQL's restricted MCV mechanism; describes the frozen training and physical evaluation protocols; and then reports the measured trade-offs and their threats to validity. Our claim is not that one objective dominates in every environment, but that **an ESS advisor's model of which schemes may be applied can materially change what it should choose**.
