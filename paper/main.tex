\section{Problem Formulation}

\subsection{Cardinality-Estimation Tasks and Resources}

Let $\mathcal I$ be a finite collection of cardinality-estimation tasks.
Task $i\in\mathcal I$ identifies a specified relational cardinality target
and its estimation context.  It may describe a selection, a join result, a
logical intermediate result, or another explicitly defined relational
expression.  A task is not necessarily an entire SQL query or a physical
execution-plan node.  Its true cardinality is $N_i\geq 0$, its positive
reference target is
\[
  T_i=\max\{1,N_i\},
\]
and its workload weight is $w_i>0$.

Let $\E$ be a finite universe of candidate estimation resources.  The
advisor chooses one global, unordered resource set $M\subseteq\E$ shared by
all tasks.  No restriction on resource arity, representation, or internal
implementation is imposed at this level.  The only resource constraint is a
maintenance budget.  Let
\[
  \operatorname{Maint}:2^{\E}\longrightarrow\mathbb R_{\geq 0}
\]
be the additional maintenance cost relative to the baseline database
maintenance process, normalized by
$\operatorname{Maint}(\varnothing)=0$.  More generally, it may depend on
fixed external conditions $\xi$, written
$\operatorname{Maint}(M;\xi)$, including the database state, data-modification
workload, refresh policy, evaluation horizon, and accounting convention.  We
abbreviate the fixed-instance function to $\operatorname{Maint}(M)$ and
require
\[
  \operatorname{Maint}(M)\leq B,\qquad B\geq 0.
\]
The function is not assumed to be additive, monotone, submodular, or
determined by per-resource coefficients.

\subsection{Admissible Schemes and Estimation Models}

For each task $i$, let $\Omega_i$ be a finite universe of complete
estimation schemes.  A scheme $\sigma\in\Omega_i$ contains all information
needed to determine how the target is estimated; depending on the underlying
system, it may encode selected resources, application order, predicate
coverage, estimator-specific choices, and context.  Define the resources it
requires by
\[
  \operatorname{used}(\sigma)\subseteq\E.
\]
The abstract admissibility interface is
\[
  \Gamma_i:2^{\E}\longrightarrow
  2^{\Omega_i}\setminus\{\varnothing\},
\]
with the consistency condition
\[
  \sigma\in\Gamma_i(M)
  \;\Longrightarrow\;
  \operatorname{used}(\sigma)\subseteq M.
\]
We require directly that
\[
  \forall i\in\mathcal I,\;\forall M\subseteq\E:
  \qquad \Gamma_i(M)\neq\varnothing.
\]
A baseline scheme $\sigma_i^{\varnothing}\in\Gamma_i(\varnothing)$ is
available at $M=\varnothing$, but it need not remain admissible for nonempty
created sets.  No monotonicity is imposed: creating additional resources need not imply
$\Gamma_i(M_1)\subseteq\Gamma_i(M_2)$ when
$M_1\subseteq M_2$.  Thus, resources created by the advisor and resources
actually used by an admissible scheme are distinct concepts.  Schemes are
not required to be sets, matchings, sequences, or execution plans.

Separately, let the black-box estimator be
\[
  \operatorname{Est}_i:\Omega_i\longrightarrow\mathbb R_{>0}.
\]
It returns the estimated cardinality of task $i$ under scheme $\sigma$.
The generic formulation imposes no algebraic structure on this function:
there is no assumption of multiplicative separability, statistical
independence, additive resource effects, or database-specific output
conversion.  Admissibility determines which schemes may occur, whereas
$\operatorname{Est}_i$ determines the estimate produced by each scheme.
Finally, let $\ell_i:\Omega_i\to\mathbb R_{\geq0}$ be a task-specific loss.
The principal illustrative choice is absolute logarithmic error,
\[
  \ell_i(\sigma)=
  \left|\log\frac{\operatorname{Est}_i(\sigma)}{T_i}\right|.
\]

\subsection{General Pessimistic Selection}

The estimator-agnostic budgeted pessimistic selection problem is
\[
\boxed{\begin{aligned}
  \operatorname*{minimize}_{M\subseteq\E}\quad
    &\sum_{i\in\mathcal I}w_i
      \max_{\sigma\in\Gamma_i(M)}\ell_i(\sigma)\\
  \text{subject to}\quad
    &\operatorname{Maint}(M)\leq B.
\end{aligned}}
\]
The decision is the created resource set $M$; the adversarial choice ranges
only over admissible schemes, and the estimator and loss evaluate those
schemes.  The individual task maxima are taken independently, so the model
need not correspond to one globally consistent adversarial policy.  In
particular, selecting more resources is not assumed to improve the objective
monotonically.  The objective concerns cardinality-estimation accuracy, not
physical plan selection or query execution time.

For a nonempty family of actual policies $\Theta$ that produces schemes
$\sigma_i(M;\theta)$ satisfying
$\sigma_i(M;\theta)\in\Gamma_i(M)$ for every relevant $i$, $M$, and
$\theta$, then, for the same loss model,
\[
  \max_{\theta\in\Theta}\sum_{i\in\mathcal I}w_i
    \ell_i\bigl(\sigma_i(M;\theta)\bigr)
  \leq
  \sum_{i\in\mathcal I}w_i
    \max_{\sigma\in\Gamma_i(M)}\ell_i(\sigma).
\]
This conditional inequality may be strict when policy choices are coupled
across tasks; it is not an unconditional guarantee about any particular
database system.  If each SQL query contributes exactly one task, then
$\mathcal I$ is equivalent to a query-indexed workload.  A query may instead
contribute several logical cardinality tasks.  Such a task specifies what is
estimated, an estimation scheme specifies how resources and estimator
decisions are used, and a physical plan specifies how execution proceeds;
these are distinct objects.

\subsection{Pairwise PostgreSQL MCV Instantiation}

We now specialize the abstract problem to the controlled single-table
conjunctive cardinality-estimation tasks considered in this study.  This
specialization is restricted to two-column PostgreSQL MCV statistics and
does not define the generic problem.

\paragraph{Pairwise admissibility.}
Each candidate $e$ covers an attribute set $A_e$ with
$|A_e|=2$.  For task $i$, let $\E_i\subseteq\E$ contain the candidates that
are structurally eligible from their statistic kind, covered columns, and
predicate operators.  These candidates form the edge-labeled multigraph
\[
  H_i=(V_i,\E_i),\qquad
  V_i=\bigcup_{e\in\E_i}A_e.
\]
Every edge retains its candidate identity; distinct statistics with the same
endpoints are parallel edges.  For a created set $M$, $H_i[M]$ contains the
eligible edges in $M\cap\E_i$.

The concrete scheme universe and resource-use mapping are
\[
  \Omega_i^{\mathrm{MM}}=\operatorname{Matchings}(H_i),
  \qquad \operatorname{used}(P)=P,
\]
where the matching universe includes the empty matching.  For a created set
$M$, the concrete admissibility rule is
\[
  \boxed{\Gamma_i^{\mathrm{MM}}(M)=
    \operatorname{MaximalMatchings}(H_i[M]).}
\]
Every maximal matching of $H_i[M]$ is a matching of the full graph, so
$\Gamma_i^{\mathrm{MM}}(M)\subseteq\Omega_i^{\mathrm{MM}}$; moreover,
$P\in\Gamma_i^{\mathrm{MM}}(M)$ implies
$\operatorname{used}(P)=P\subseteq M$.  Finite graphs always have a maximal
matching, including the unique empty matching of an edgeless graph, so this
rule satisfies the generic nonemptiness requirement.

A matching is a set of edges with no shared endpoint.  It is maximal if no
additional available edge can be added while preserving that property;
maximal does not mean maximum cardinality.  This rule is a deliberate
abstraction of a restricted
PostgreSQL estimator behavior motivated by compatible clause coverage.  It
is not a universal characterization of PostgreSQL, arbitrary predicates,
join or intermediate-result estimation, or statistics with more than two
attributes.

\paragraph{Pre-clamp multiplicative estimator.}
Let $n_i^0>0$ be the baseline pre-clamp cardinality estimate and let
$r_{e,i}>0$ be a fixed correction factor for each eligible candidate.  For a
matching $P\in\Gamma_i^{\mathrm{MM}}(M)$, define
\[
  \boxed{\operatorname{Est}_i^{\mathrm{mult}}(P)=
    n_i^0\prod_{e\in P}r_{e,i}.}
\]
The factors are calibrated from full-precision, pre-clamp estimation
quantities rather than rounded displayed \texttt{Plan Rows}.  This is the
explicit assumption of multiplicative separability: a factor is fixed for a
task and does not depend on which other compatible resources are used.  It
does not assert independence of the underlying attributes; a multivariate
statistic may encode dependence within its own attribute group.  Define
\[
  \alpha_i=\log\frac{n_i^0}{T_i},\qquad
  b_{e,i}=\log r_{e,i}.
\]
The resulting raw loss is
\[
  \ell_i^{\mathrm{raw}}(P)=
  \left|\alpha_i+\sum_{e\in P}b_{e,i}\right|.
\]

For comparison with finalized PostgreSQL row estimates, the concrete
instantiation may apply the implementation-scoped transformation
\[
  C_{\mathrm{PG}}(x)=
  \begin{cases}
    1,&0<x\leq 1,\\
    \operatorname{rint}(x),&1<x\leq x_{\max},
  \end{cases}
\]
for finite positive $x$ in the ordinary regime.  Here $x_{\max}$ denotes
the implementation's finite cap and $\operatorname{rint}$ follows its
floating-point rounding mode; nonfinite inputs and other very-large-value
paths are outside this instantiation.  The corresponding secondary plan
loss is
\[
  \ell_i^{\mathrm{plan}}(P)=
  \left|\log C_{\mathrm{PG}}
    \bigl(\operatorname{Est}_i^{\mathrm{mult}}(P)\bigr)-\log T_i\right|.
\]
Raw and plan loss are distinct objectives and need not have the same
optimizer.  In the remainder, raw loss is the primary theoretical
convention.

\paragraph{PostgreSQL maintenance cost.}
For the controlled PostgreSQL instance, assume PostgreSQL 16.14 and
two-column MCV objects.  For each relevant table $t$, let $S_t$ denote one
fixed realized sample of table tuples, and let $\widehat R_t$ be its
associated estimated total row count supplied to the statistics-building
procedure.  Across compared resource selections, the actual tuple contents
of $S_t$, including relevant attribute values, $\widehat R_t$, candidate
definitions, effective statistics targets, relation schema, data types,
collations, and other relevant build and estimator settings are fixed.  The
reference sample must be adequate for the statistics-target requirements of
all considered candidates.  Candidate selection does not change the shared
sample-acquisition workload.  Thus, the complete sample-derived MCV build
input, rather than only its tuple count, is controlled in the fixed
evaluation environment.

This is an experimental and mathematical control assumption, not a claim
that standard PostgreSQL reuses identical random samples across repeated
\texttt{ANALYZE} executions; no sample-fixing capability is presumed to be
implemented here.  Fixing $S_t$ and its associated metadata makes candidate
statistics comparable, but does not establish multiplicative separability.
That separability remains the explicit estimator assumption above.  Likewise,
fixed sampling and sequential per-object construction do not imply additive physical
CPU time.

Let $p_e(S_{t(e)})\geq0$ denote the modeled additional CPU work, in
CPU-seconds, attributable to refreshing candidate MCV $e$ once, conditioned
on the fixed reference sample and controlled PostgreSQL environment.  Its
intended full-refresh scope includes candidate-specific build-data
preparation, MCV construction, MCV serialization, and attributable CPU work
of persisting the statistics result.  Shared sample acquisition and baseline
single-column statistics maintenance are excluded.  CPU-seconds measure
computing work, not wall-clock response time; memory peaks and I/O bytes are
not additional terms in this scalar budget without a separate conversion
model.  The coefficient is a defined, presently uncalibrated model
parameter: a catalog-free offline profiler can directly measure
construction-related work, but catalog-update overhead requires separate
estimation or calibration if complete refresh overhead is intended.

Let $\nu_t\geq0$ be the externally specified expected number of refreshes for
table $t$ during the fixed evaluation horizon.  Define
\[
  \bar m_e=\nu_{t(e)}p_e(S_{t(e)}),
  \qquad
  \boxed{\widehat{\operatorname{Maint}}^{\mathrm{PG}}(M)=
    \sum_{e\in M}\bar m_e.}
\]
This is a reference-sample-based period-level proxy.  Using one per-refresh
coefficient over multiple refreshes assumes that it is sufficiently
representative of that period; it does not claim that future \texttt{ANALYZE}
executions reuse the same tuples.  Changes in table contents, value widths,
data distributions, or maintenance workload may change realized costs.
The refresh counts and horizon are fixed external inputs, not advisor
decisions, and neither the coefficients nor the representative-sample
assumption has yet been experimentally validated.

\paragraph{Concrete optimization problem.}
Substituting the pairwise admissibility rule, raw loss, and PostgreSQL
maintenance proxy into the general problem gives
\[
\boxed{\begin{aligned}
  \operatorname*{minimize}_{M\subseteq\E}\quad
    &\sum_{i\in\mathcal I}w_i
      \max_{P\in\operatorname{MaximalMatchings}(H_i[M])}
      \left|\alpha_i+\sum_{e\in P}b_{e,i}\right|\\
  \text{subject to}\quad
    &\sum_{e\in M}\bar m_e\leq B.
\end{aligned}}
\]
Here $B$ is measured in CPU-seconds over the fixed evaluation horizon.
This is a concrete maintenance-cost specialization; it does not impose
additivity on the abstract function $\operatorname{Maint}$.  The numerical
cost coefficients and the resulting optimization are not claimed to have
been empirically validated here.
